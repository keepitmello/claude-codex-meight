# 난이도를 워커 승급으로 받을 것인가, 단계 추가로 받을 것인가

DATE: 2026-07-29 · FORK: user-decided during dispatcher-side policy edit

BACKGROUND: worker 기본값에서 Fast를 내리는 작업 도중, 디스패처가 "난이도가
높으면 worker 모델을 `sol medium` → `sol high`로 올린다"는 사다리를 정책에
넣었다. 사용자가 두 가지를 짚었다: (a) 모델 라우팅 하드게이트를 목록으로
박아두는 것보다 디스패처가 판단하게 하는 게 낫고, 그런 작업도 `medium`이
해내는 경우가 많다. (b) `sol high`에게 구현을 시키는 건 인력·토큰 낭비다 —
`sol`에게 설계를 시키고 `luna` 워커가 구현하는 구조가 가장 좋다.

(b)는 이미 이 하네스의 원형 파이프라인이다(blind design → plan-review →
worker 구현 → 적대 리뷰). 사다리는 그 구조를 흐리는 방향이었다: 난이도의
대부분은 판단에 있는데, 워커 브레인을 키우는 건 실행 쪽 축을 올리는 것이다.

DECISION:

1. 난이도 대응의 1순위는 **단계 추가**다: `sol` mate 플랜 → 동결 → `luna`
   워커 구현. 가장 싼 강한 조합이고 이 하네스의 기본 구조다.
2. worker 자세의 `sol`은 예외 경로로 강등한다 — 설계를 앞에 붙일 수 없거나
   플랜을 쥐고도 구현이 어려울 때. `medium`이 먼저다.
3. `sol high`는 어느 자세든 띄우기 전 사용자 확인 1회 (가장 비싼 조합, 비용
   있는 실행은 사용자 소유 결정). 구현에 `sol high`가 필요해 보이면 대개
   앞단 설계가 빠졌다는 신호로 읽고 mate 한 판을 먼저 검토한다.
4. `sol`의 effort 상한은 `high`. `sol xhigh`는 선택지에서 제거한다.
5. 모델 라우팅의 하드게이트 **목록을 폐지**한다. 남는 건 원칙 하나 — 실패가
   돈·데이터를 손상시키거나 되돌릴 수 없거나 프로덕션에 크게 번지면 브레인을
   올린다. 열거는 판단을 대체하지 못하고, 이름이 무거운 작업(동시성,
   마이그레이션)도 잘 정의돼 있으면 `luna`/`sol medium`이 해낸다. 올렸으면
   무엇을 보고 올렸는지 한 줄로 말한다.
6. 유지되는 것: 돈 경로 디스패처 sign-off, worker 스킬의 "혼자 결정 금지"
   에스컬레이션 목록(보안·비가역, 공개 schema/API 계약, 영속 데이터
   마이그레이션, 돈 경로, 동결 플랜). 이건 모델 라우팅이 아니라 워커 소유권
   경계라 성격이 다르다.
7. 세션을 띄우면 어떤 모델·effort로 띄웠는지 사용자에게 한 줄 보고한다.
   백그라운드 세션은 사용자 눈에 안 보이므로 이 한 줄이 비용과 브레인 티어를
   아는 유일한 창이다.

REVISIT WHEN: mate 플랜을 받은 `luna` 워커가 반복해서 구현에 실패한 실측이
lessons.md에 쌓이면 2를 재검토한다. 하드게이트 목록 폐지 후 브레인을 올렸어야
할 작업을 `luna`로 보낸 사고가 나면 5를 재검토한다.
